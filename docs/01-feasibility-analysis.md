# Mythicraft 可行性分析

> 文档状态：设计基线
>
> 适用范围：Rust 独立 Minecraft RPG 服务端核心 + 客户端 Mod
>
> 核心前提：第一版不做地形生成，优先读取已有 Minecraft 地图存档。

## 1. 结论

项目在工程上可行，且“固定地图 + RPG 专用逻辑 + 客户端 Mod”这一取舍能显著降低第一版复杂度。最合理的产品定位是：

> 一个以已授权 Pumpkin Rust 核心为底座、针对 RPG 场景优化的 Minecraft 专用服务端运行时，提供 Paper 常用配置导入、MythicMobs/Vault 语义兼容子集和既有地图读取能力。

不应把第一版承诺为“Paper 的 Rust 重写”或“可以直接运行所有 Paper 插件”。Paper 插件依赖 JVM、Bukkit/Paper 类和具体生命周期，Rust 核心无法仅靠读取 `plugin.yml` 或 YAML 配置直接执行这些插件。

## 2. 需求拆解与可行性

| 目标 | 可行性 | 第一版建议 | 关键限制 |
| --- | --- | --- | --- |
| Pumpkin 底座 + Mythicraft RPG 领域层 | 高 | 复用 Pumpkin 的网络、世界、实体和 tick；实现 RPG/兼容/客户端适配 | 需要锁定 Pumpkin 版本、Minecraft 版本和协议实现范围 |
| 面向 RPG 场景优化 | 高 | 固定地图、有限区块、事件驱动技能和实体系统 | 不追求完整生存模式兼容 |
| 读取既有 Minecraft 地图 | 高 | 读取 Anvil `.mca`、NBT、区块调色板和基础实体 | 需明确 `DataVersion`，不承诺任意版本无损读取 |
| 不实现地形生成 | 高 | 服务器只加载已有区块，未保存区块拒绝进入或返回配置的边界 | 仍需处理区块加载、卸载和碰撞数据 |
| 兼容 Paper 配置 | 中高 | 提供配置导入器、映射规则和诊断报告 | 通用插件配置没有统一 schema，不能自动理解所有字段 |
| 内置 MythicMobs | 中高 | 解析常用 YAML，编译成 Mythicraft 中间表示 | 复杂机制、脚本扩展和第三方条件需要逐项适配 |
| 内置 Vault 能力 | 高 | 原生提供 Economy、Permission、Chat 服务接口 | 兼容 Vault 的概念和配置，不运行 Vault.jar |
| 客户端 Mod 提供 UI/贴图/音效 | 高 | 使用稳定的自定义 payload 协议和资源包版本 | 客户端 Mod 需与协议、Minecraft 版本配套 |
| 运行现有 Paper 插件二进制 | 低 | 明确排除；未来另行设计桥接沙箱 | 需要 JVM、Paper API 模拟和大量未定义行为兼容 |

## 3. 产品边界

### 3.1 第一版必须完成

1. 锁定一个 Minecraft Java Edition 版本和对应客户端 Mod 版本。
2. 支持登录、握手、玩家进出、基础区块发送和基础移动同步。
3. 从 `level.dat`、region 文件和区块 NBT 中读取固定地图。
4. 支持固定地图中的方块、基础碰撞、出生点、世界时间和玩家位置保存。
5. 在 Pumpkin 权威 tick 循环上接入 Mythicraft RPG 事件和状态提交。
6. 提供 RPG 所需的实体、属性、伤害、技能、掉落、任务事件和状态效果最小模型。
7. 导入并执行约定范围内的 Paper/MythicMobs/Vault 配置。
8. 通过客户端 Mod 显示自定义 HUD、菜单、字体/图标、音效和服务端事件。
9. 对未支持的配置字段输出带路径、原因和建议的诊断报告，不静默忽略。

### 3.2 第一版明确不做

- 任意版本兼容。
- 地形生成、种子生成、完整生存玩法和红石模拟。
- 运行任意 Bukkit、Spigot、Paper Java 插件。
- 直接加载第三方 `.jar` 并假设其行为可迁移。
- 完整复刻 MythicMobs 的全部机制、脚本和第三方扩展。
- 客户端无需安装 Mod 就能获得所有自定义 UI、贴图和音效。
- 将 Mojang 客户端或资源资产打包到本项目中。

## 4. 推荐总体架构

```text
客户端 Mod
  ├─ 原版 Minecraft 协议
  └─ Mythicraft Custom Payload（能力协商、UI、资源、音频、事件）
                         │
                网络会话与协议层
                         │
                 Rust 服务端运行时
  ┌──────────┬───────────┼────────────┬──────────────┐
  │ 世界读取 │ ECS/实体   │ RPG 规则   │ 配置兼容层    │
  │ Anvil/NBT│ Tick/Event │ 技能/伤害  │ Paper/Mythic/Vault│
  └──────────┴───────────┴────────────┴──────────────┘
                         │
              持久化、日志、指标、管理工具
```

### 4.1 网络与会话层

负责 Minecraft 协议状态机、压缩/加密、登录模式、玩家会话、包编解码、区块发送和自定义 payload。建议第一版只支持一种明确的协议版本，协议版本升级通过适配层完成，不把所有版本差异散落在业务代码中。

客户端 Mod 连接后应先发送协议版本和能力集，服务端据此决定是否启用自定义 UI、音频和资源能力。能力不匹配时必须给出可读错误，而不是让玩家进入半可用状态。

### 4.2 世界层

世界层建议分为两部分：

- `StaticWorld`：从 Anvil/NBT 读取的只读地图数据，包括区块、方块状态、方块实体、出生点和基础世界信息。
- `DynamicWorld`：玩家、RPG 怪物、掉落物、状态、临时方块和运行时事件。

这样可以避免把静态地图数据和频繁变化的实体状态混在同一个持久化模型中，也方便后续做只读地图缓存。第一版可限制为单世界、有限区块白名单和预加载区域。

地图读取至少需要覆盖：

- `level.dat` 中的世界元数据、`DataVersion`、出生点和时间。
- `region/r.x.z.mca` 中的 chunk NBT。
- 区块 section 的 palette、block states、光照数据和高度信息。
- 需要参与 RPG 逻辑的方块实体和基础实体数据。
- 原始 NBT 的诊断信息，以便出现未知字段时定位问题。

地图读取器应先做离线检查工具，再接入在线服务器。离线工具可以输出地图版本、区块范围、未知 tag、损坏 region 和预估内存占用。

必须额外维护版本对应的方块状态注册表和协议 ID 映射。Anvil 中的 palette 值只有结合目标 Minecraft 版本的 registry 才能还原为可发送给客户端的方块状态；不能把存档中的数字值当作跨版本稳定 ID。

地图存档只是静态世界数据，不自动携带完整的原版行为。命令方块、数据包、红石、原版实体 AI、未实现的方块实体和依赖 Paper 生命周期的逻辑，都必须单独列入支持矩阵；读取成功不代表这些行为会被执行。

### 4.3 模拟与 ECS

第一版采用“单线程权威 tick + 可并行的只读任务”更容易保证确定性：

- 20 TPS，每个 tick 的逻辑预算为 50 ms。
- 玩家输入、技能、伤害和事件按固定阶段处理。
- 路径搜索、资源加载、地图解压等可放到异步任务，但结果只能在明确 tick 边界提交。
- 不要让网络线程直接修改世界状态。

Rust 能减少 GC 抖动和共享可变状态错误，但性能并不会自动产生。真正需要测量的是 tick p95/p99、区块发送延迟、网络包量、实体查询耗时和内存峰值。

### 4.4 RPG 规则层

规则层不要直接依赖 YAML 字段或网络包。应先把配置编译为稳定的中间表示（IR），例如：

- `RpgEntityDefinition`
- `AttributeDefinition`
- `SkillDefinition`
- `Condition`
- `Effect`
- `DamageEvent`
- `LootTable`

运行时只消费 IR。这样既能支持 MythicMobs 导入，也能让未来的原生 Rust 配置、编辑器或其他导入器复用同一运行时。

## 5. Paper、MythicMobs 与 Vault 兼容策略

### 5.1 三种兼容级别

必须在产品和代码中区分以下三种含义：

1. **文件兼容**：可以读取已有配置、地图和资源文件。
2. **语义兼容**：同一配置在支持范围内产生相近的游戏行为。
3. **二进制/API 兼容**：已有 Java 插件无需修改即可运行。

Mythicraft 第一版目标是前两种，不承诺第三种。

### 5.2 Paper 配置迁移

Paper 本身以及插件生态没有单一的通用配置 schema。建议提供显式迁移管线：

```text
原始配置 → 语法解析 → 字段映射 → 兼容 IR → 校验 → 迁移报告 → 运行时
```

迁移器需要保留：原始文件路径、字段路径、目标字段、转换规则、警告级别和来源行号。建议报告分为：

- `supported`：可以直接使用。
- `converted`：经过单位、名称或结构转换后使用。
- `partial`：只支持字段的一部分。
- `unsupported`：明确不支持，阻止生产启动或由配置决定是否降级。
- `invalid`：格式错误或类型不匹配。

不能仅凭文件名把任意插件配置归类为可执行配置。每个受支持配置族都应有版本化 schema 和 golden test。

### 5.3 MythicMobs

建议按功能分层支持，而不是一次性声称“兼容 MythicMobs”：

**P0：** 怪物基础属性、生命/伤害、防御、目标、名称、AI 基础行为、掉落、生成点引用。

**P1：** 技能触发器、冷却、条件、伤害、击退、状态效果、粒子/音效事件、范围和目标选择。

**P2：** 复杂脚本、变量、跨插件条件、特殊机制、第三方扩展和高度依赖 Bukkit API 的动作。

解析器必须避免把 YAML 直接解释成运行时反射调用。推荐：

1. 解析 YAML 为带 source location 的 AST。
2. 将 mechanic、trigger、condition 映射到版本化 IR。
3. 对未知节点返回结构化诊断。
4. 对无法等价实现的机制提供明确替代策略或禁用策略。
5. 对同一配置生成稳定的内容 hash，便于缓存和增量重载。

### 5.4 Vault

Vault 更适合做“服务接口兼容”，而不是文件或二进制兼容。服务端原生提供：

- Economy：余额、存款、取款、货币名称和交易结果。
- Permission：玩家/组权限查询。
- Chat：前缀、后缀和格式化上下文。

RPG 逻辑应只依赖 Mythicraft 自己的服务接口；兼容层负责读取常见 Vault/Paper 配置并把调用映射到原生服务。所有经济变更必须使用幂等交易 ID、审计日志和原子提交，避免断线或重复事件造成刷钱。

### 5.5 为什么不直接兼容 Paper 插件

Paper 插件通常依赖：

- JVM 类加载和 Java 字节码。
- Bukkit/Paper API 的对象模型、事件总线和线程约束。
- NMS 内部类和具体 Minecraft 版本实现。
- 其他插件提供的服务注册与生命周期。

Rust 核心无法通过“实现几个接口”覆盖这些隐含契约。未来若确实需要扩展能力，应优先设计 Rust/WASM 原生插件 API；JVM 桥接只能作为隔离、受限、成本高的实验性路线，不能作为第一版依赖。

## 6. 客户端 Mod 与自定义内容

客户端 Mod 负责展示和播放，服务端保持权威：

- 服务端发送 UI 状态、页面模型、按钮动作和事件 ID。
- 客户端只回传经过 schema 校验的用户动作，不直接提交伤害、掉落或货币结果。
- 贴图、字体和音效按资源包版本管理，资源 hash 不一致时拒绝或降级。
- 所有自定义 payload 都应有协议版本、消息类型、请求 ID、长度上限和权限检查。
- 客户端 Mod 可选择 Fabric 或 NeoForge，但第一版只选一个，并锁定 Minecraft 版本。

建议把协议分为：

- `hello/capabilities`
- `ui.open`, `ui.update`, `ui.close`
- `ui.action`
- `asset.manifest`
- `audio.play`
- `rpg.combat_event`
- `rpg.dialogue_event`

UI 协议最好传输数据模型而非任意客户端代码，以便服务端热更新内容并控制安全边界。

## 7. 性能与容量目标

Rust 的收益主要来自可预测的内存管理、较低的运行时开销和更容易做数据导向设计；收益必须用基准测试证明。建议第一版把目标写成可测量的门禁，而不是宣传语：

| 指标 | 开发基线 | 说明 |
| --- | --- | --- |
| tick 频率 | 20 TPS | 固定地图 RPG 核心目标 |
| tick p95 | ≤ 35 ms | 留出网络和系统抖动空间 |
| tick p99 | ≤ 50 ms | 超过则记录慢 tick 样本 |
| 逻辑线程阻塞网络 | 0 次 | 网络 IO 不得阻塞权威模拟 |
| 地图加载 | 按白名单预加载 | 第一版不做无限世界加载 |
| 实体更新 | 以可见性/区域分桶 | 避免每 tick 全量扫描 |
| 配置重载 | 原子切换版本 | 失败时保留上一份有效配置 |

这些数值是初始工程门槛，不是最终容量承诺。正式容量需要在目标机器、目标地图和目标 RPG 配置上压测。

## 8. 主要风险与缓解措施

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 协议版本变动 | 客户端无法连接 | 第一版锁版本；协议适配单独封装；建立协议回归样本 |
| 地图 NBT/DataVersion 差异 | 方块或实体读取错误 | 先做离线导入检查；允许配置转换；拒绝未知高风险版本 |
| MythicMobs 语义过宽 | 迁移后行为不一致 | 分级支持；IR；golden test；启动时输出报告 |
| Paper 插件依赖 API | 生态无法直接迁移 | 明确二进制不兼容；提供原生 API 和适配模板 |
| tick 尖峰 | 战斗卡顿、玩家掉线 | 阶段化 tick、区域分桶、慢 tick 诊断和压测门禁 |
| 经济一致性问题 | 刷钱或数据损坏 | 事务 ID、审计日志、原子存档和故障注入测试 |
| 自定义 payload 被伪造 | UI/交易逻辑被绕过 | 服务端权威校验、长度限制、权限和速率限制 |
| 直接复用第三方实现 | 授权和维护风险 | 只实现公开协议/配置语义；不打包第三方 jar 或 Mojang 资产 |

## 9. 推荐技术路线

建议的技术组合：

- Rust workspace 管理核心、工具和测试夹具。
- Tokio 或等价异步运行时负责网络与非权威 IO。
- 独立 NBT/Anvil 读取模块，所有格式转换集中在 world crate。
- ECS 仅用于高频实体组件；配置和服务注册使用普通 Rust 类型。
- Serde 用于内部配置/IR 序列化，但 YAML 解析结果必须经过 schema 校验。
- tracing + metrics 记录 tick、网络、导入和经济事务指标。
- Criterion 或等价基准框架做区块解码、实体查询、技能执行和序列化基准。
- 客户端 Mod 单独目录和构建系统，与服务端协议 fixture 共享测试样本。

具体库版本不应在这份可行性文档中提前锁死，应在 M0 通过小型 spike 验证后记录到版本矩阵。

## 10. 第一版验收标准

当以下条件同时满足时，第一版可以称为“可试玩技术预览”：

1. 指定版本的客户端原版可完成基础登录，安装 Mod 的客户端可完成能力协商。
2. 给定的地图样本能通过离线检查并在服务端启动后读取出生区域。
3. 玩家能在地图内移动、碰撞、重连，并恢复位置和基础 RPG 状态。
4. 一个 MythicMobs 兼容样例能导入并执行怪物、技能、伤害和掉落闭环。
5. 一个 Vault 兼容样例能完成余额查询、扣款、奖励和审计查询。
6. 客户端能打开一套 UI、显示自定义图标并播放服务端触发的音效。
7. 不支持配置会在启动或导入阶段被报告，不会静默改变玩法。
8. 基线压测达到 tick p95/p99 门槛，并生成可复现报告。
9. 服务器在断电/强制退出模拟后能恢复到一致的持久化状态，或明确报告损失边界。

## 11. 最终建议

建议立项，但先做 2—4 周的 Pumpkin-backed 垂直切片，而不是立即铺开完整服务端：

```text
固定版本协议登录
  → 读取一个真实地图样本
  → 玩家移动与区块发送
  → 一个 MythicMobs 怪物/技能
  → 一个 Vault 经济交易
  → 一个客户端 UI/音效事件
```

只要这条链路能在明确的数据和版本范围内跑通，项目的主要技术风险就从“是否能做”转为“兼容范围和内容规模如何控制”。
