# Mythicraft 面向 AI 的开发计划

> 文档用途：作为 AI 编码代理、人工开发者和代码评审的共同执行协议。
>
> 当前状态：Pumpkin 原生核心接入已开始并完成第一层生命周期挂接；本文档描述后续实现、验证和发布执行顺序。当前仍未完成 RPG 技能执行、持久化、真实客户端 smoke test 和完整兼容矩阵。

## 1. AI 开发总原则

AI 代理每次工作都必须以可验证的小步提交为单位。任何代理都不能把“看起来像 Paper”当成兼容证明，也不能在没有 fixture、测试或诊断报告的情况下宣称配置迁移完成。

### 不可违反的边界

- 第一版固定一个 Minecraft 版本、一个客户端 Mod 加载器和一个地图格式版本范围。
- Rust 服务端是权威状态源；客户端只负责展示、输入和播放。
- RPG、经济、权限和客户端 payload 的权威状态直接编译进 Pumpkin 的 `MythicraftCore`；独立 WIT/插件边界只用于非核心扩展。
- 不执行未审核的 Java 插件代码，不加载任意网络脚本，不通过反射绕过 schema。
- 不把原始 YAML 直接传入 tick 逻辑；必须先编译为版本化 IR。
- 不静默忽略未知配置、未知 NBT tag 或未知 payload。
- 不在网络线程直接修改世界状态。
- 不在权威 tick 中做无界 IO、同步文件访问或全量实体扫描。
- 不提交 Mojang 客户端、第三方插件 jar 或未经确认授权的资源资产。

## 2. 目标仓库布局

建议在实现阶段采用以下结构；如果 spike 证明某个 crate 不需要，可在 ADR 中记录调整原因：

```text
mythicraft/
├─ Cargo.toml
├─ crates/
│  ├─ protocol/       # Minecraft 包与 Custom Payload 编解码
│  ├─ session/        # 登录、玩家会话、连接生命周期
│  ├─ world/          # Anvil/NBT 读取、区块模型、地图检查
│  ├─ simulation/     # tick 调度、阶段、事件提交
│  ├─ entity/         # ECS 组件、查询、可见性和区域分桶
│  ├─ rpg/            # 属性、技能、伤害、效果、掉落
│  ├─ compat/         # Paper/MythicMobs/Vault 导入和诊断
│  ├─ api/            # Rust 原生扩展 API 与服务接口
│  ├─ persistence/    # 玩家、经济、运行时状态存档
│  └─ observability/  # tracing、metrics、慢 tick 报告
├─ server/            # 可执行服务端入口、命令和默认配置
├─ tools/
│  └─ map-inspector/  # 离线地图检查和导入报告工具
├─ client-mod/        # Fabric 或 NeoForge 客户端 Mod
├─ fixtures/          # 协议、NBT、配置和语义 golden fixtures
├─ docs/
└─ tests/             # 跨 crate 集成和黑盒测试
```

服务端 crate 不应依赖客户端 Mod 的实现；双方只共享协议 schema、版本号和测试样本。

## 3. 版本矩阵与 ADR

在写核心业务前，AI 代理必须创建版本矩阵，至少包括：

| 项目 | 必须记录 |
| --- | --- |
| Minecraft | Java 版本、协议版本、DataVersion |
| 服务端 | Rust toolchain、目标平台、构建 profile |
| 客户端 | Mod loader、loader 版本、Mod 版本 |
| 地图 | Anvil/NBT 版本、是否含实体/方块实体、区块范围 |
| 兼容配置 | Paper/MythicMobs/Vault 的来源版本和支持等级 |

以下决策必须写成短 ADR：

- 为什么选择固定 Minecraft 版本。
- 为什么选择 Fabric 或 NeoForge。
- ECS/实体存储的选择和并行边界。
- 自定义 payload 的编码格式和兼容策略。
- 地图静态层与动态层的持久化边界。
- 未来原生插件 API 是 Rust ABI、WASM 还是进程外 RPC。

ADR 只记录已验证的决定、替代方案、代价和回滚条件，不把猜测写成事实。

## 4. 里程碑与门禁

### M0：规格冻结与技术 spike

**目标：** 消除版本和关键格式的不确定性。

**AI 任务：**

- 建立版本矩阵和协议能力表。
- 选定一个公开、可测试的地图样本来源和许可记录。
- 选择 NBT/Anvil 解析方案，完成 `level.dat` 和一个 region 的读取 spike。
- 选择客户端 Mod loader，完成空 Mod 与服务端 custom payload 的互通 spike。
- 写出第一版配置支持清单和不支持清单。

**通过条件：**

- 能输出地图的 `DataVersion`、坐标范围和区块计数。
- 客户端能发送/接收带版本号的 hello payload。
- 关键选择都有 ADR，且不存在未解决的版本歧义。

### M1：协议与会话骨架

**目标：** 原版客户端能连接，服务端能管理会话。

**交付：**

- 包编解码、状态机、压缩/加密边界和连接错误模型。
- 玩家 join/quit、keep-alive、基础聊天/命令反馈。
- custom payload 的长度限制、消息类型和能力协商。
- 协议 fixture 与 round-trip 测试。

**通过条件：**

- 多次连接/断开不会泄漏任务或玩家状态。
- 非法长度、未知消息和错误版本被安全拒绝。
- 网络 IO 与 tick 状态修改通过消息队列或 tick 提交点隔离。

### M2：固定地图读取与区块服务

**目标：** 从真实地图提供可探索的静态世界。

**交付：**

- `map-inspector` 命令行工具。
- Anvil region 解压、NBT、palette/block state 和基础光照读取。
- 区块白名单、预加载、缓存、卸载和读取错误处理。
- 地图坐标、出生点和世界时间模型。
- 地图读取 golden fixtures。

**通过条件：**

- 检查工具能区分损坏、未知版本和空区块。
- 服务端能向客户端发送出生区域，且玩家重连后位置稳定。
- 未加载/未允许区块不会被隐式生成。

### M3：权威 tick 与基础实体

**目标：** 建立可预测的游戏循环。

**交付：**

- 20 TPS 固定阶段：输入、脚本事件、AI、物理/碰撞、效果、输出、持久化提交。
- 玩家移动校验和基础碰撞。
- ECS 组件、实体 ID、区域分桶、可见性过滤。
- 事件总线和 tick 内延迟提交。
- 慢 tick tracing 和基准测试。

**通过条件：**

- 同一输入 fixture 在同一配置下得到相同的状态摘要。
- tick p95 ≤ 35 ms、p99 ≤ 50 ms 的开发基线在固定压测场景中成立。
- 无同步磁盘 IO 位于权威 tick 路径。

### M4：RPG 原生模型

**目标：** 让一个 RPG 战斗闭环脱离兼容层运行。

**交付：**

- 属性、资源、等级、状态效果和抗性。
- 目标选择、技能触发、冷却、条件、效果和伤害事件。
- 怪物定义、生成、仇恨和基础 AI。
- 掉落表、物品定义和事件日志。
- 规则 IR 的版本号与校验器。

**通过条件：**

- 不通过网络输入直接设置生命、伤害、掉落或货币。
- 每个战斗结果可用事件 ID 追踪到触发源。
- 技能执行在无客户端连接时仍能保持服务端状态正确。

### M5：兼容导入器

**目标：** 迁移一个真实 RPG 配置样例。

**交付顺序：**

1. 通用 YAML 语法、类型和 source location 诊断。
2. Paper 常用服务器设置映射。
3. MythicMobs P0 怪物/技能/掉落子集。
4. Vault Economy/Permission/Chat 原生服务。
5. 导入报告、schema 版本和 dry-run 模式。

**通过条件：**

- 每个支持字段都有 source fixture 和目标 IR fixture。
- 迁移报告列出所有 `partial`、`unsupported` 和 `invalid` 项。
- 兼容层不依赖 Bukkit/Paper jar。
- 经济变更具备事务 ID、审计记录和重复提交保护。

### M6：客户端 Mod 体验层

**目标：** 交付 RPG 专用 UI、资源和音频最小闭环。

**交付：**

- hello/capability 协商和协议版本校验。
- HUD、对话框、技能栏或背包扩展中的至少一套 UI。
- 资源 manifest、hash、版本切换和缺失资源提示。
- 音效播放事件、距离/音量参数和客户端限流。
- UI action 的服务端验证和错误回传。

**通过条件：**

- 客户端无法通过伪造 UI action 获得未授权结果。
- 服务端能对不支持的客户端能力降级或拒绝连接。
- 资源与协议版本不匹配时不会静默显示错误素材。

### M7：存档、恢复与管理能力

**目标：** 具备可长期运行的基础。

**交付：**

- 玩家位置、属性、物品、任务和经济存档。
- 原子写入、版本迁移、备份和恢复命令。
- 管理命令、配置 dry-run、热重载边界。
- 崩溃恢复和断电故障注入测试。

**通过条件：**

- 重复启动不会覆盖有效存档。
- 配置重载失败保留上一份有效版本。
- 经济、物品和任务状态的一致性边界有文档和测试。

### M8：压测、安全与可发布预览

**目标：** 把垂直切片变成可交付技术预览。

**交付：**

- 固定地图、玩家数量、实体数量和技能频率的可复现压测。
- 网络模糊测试、NBT 恶意样本、YAML 资源限制和 payload 限制。
- 运行手册、故障排查、版本升级和兼容性表。
- CI 中的格式、编译、单元、集成、golden、基准和安全门禁。

**通过条件：**

- 所有 M0—M7 验收条件都有自动或人工可重复验证步骤。
- 已知不支持项在发布说明中列出。
- 目标平台安装包能在干净环境启动并读取样例地图。

## 5. AI 代理执行流程

每个 AI 任务都按以下顺序执行：

1. **读取上下文**：先读 `README.md`、相关 ADR、目标 crate 和现有测试；确认没有覆盖范围更深的 `AGENTS.md`。
2. **定义边界**：写出本任务不解决的相邻问题，列出输入、输出和错误行为。
3. **先写 fixture/test**：格式、协议和兼容行为优先建立最小反例。
4. **实现最小垂直切片**：只实现通过当前里程碑所需的路径，不引入未使用的抽象。
5. **验证**：运行最具体的测试，再运行受影响 workspace 的检查和基准。
6. **记录变化**：更新 ADR、兼容矩阵、迁移报告样例或运行手册。
7. **交付摘要**：说明修改文件、验证命令、未解决问题和下一依赖任务。

如果测试失败，AI 代理必须先判断失败是否由本任务引起；不得为了让 CI 变绿而放宽安全校验、删除 fixture 或修改无关测试。

## 6. 推荐任务格式

每个 issue 或 AI prompt 使用以下模板：

```text
任务 ID：MC-XXXX
目标：用一句话描述用户可观察的结果。
前置条件：版本矩阵、依赖任务、fixture。
范围内：明确允许修改的 crate、协议消息或配置族。
范围外：明确不实现的相邻能力。
约束：线程模型、错误处理、安全、兼容级别和性能门禁。
验收：列出可执行的 Given/When/Then 条件。
测试：单元、集成、golden、模糊、基准或手工步骤。
交付：代码、fixture、文档、诊断样例和验证结果。
```

### 示例任务

```text
任务 ID：MC-WORLD-001
目标：map-inspector 能读取一个 region 文件并报告 chunk 坐标与 DataVersion。
前置条件：已锁定 Minecraft 版本；fixtures/maps/basic/ 存在样例文件。
范围内：crates/world、tools/map-inspector、地图 fixture。
范围外：在线区块发送、方块修改、地形生成。
约束：损坏压缩数据必须返回结构化错误；不得 panic；限制单文件解压内存。
验收：有效 region 输出确定性 JSON；损坏 region 显示文件和 chunk 坐标；未知版本为 warning 或 error。
测试：有效样例、损坏样例、空 chunk、超大 NBT、重复运行一致性。
交付：代码、测试、命令使用说明和已知限制。
```

## 7. 测试策略

### 单元测试

- 包编解码、VarInt、压缩、NBT tag、palette 解码。
- 配置类型转换、单位换算、字段路径和诊断等级。
- 属性计算、伤害、冷却、条件和掉落。
- 经济事务幂等、权限匹配和资源 hash。

### Golden 测试

- Minecraft 协议包的输入/输出字节样本。
- `level.dat`、region、chunk section 和方块实体。
- MythicMobs YAML 到 IR 的结构化结果。
- Vault 配置到服务定义的结果。
- 客户端 payload schema 与协议错误。

Golden 文件需要记录来源版本和许可信息；变更必须说明原因，禁止无理由批量刷新。

### 集成测试

- 客户端连接、能力协商、区块读取、移动和断线重连。
- 怪物生成到战斗、死亡、掉落和经济奖励的闭环。
- UI action 的合法、过期、重复、越权和速率超限场景。
- 存档写入、崩溃恢复和版本迁移。

### 模糊与安全测试

- 任意网络包长度、未知消息类型和截断包。
- 损坏/递归/超大 NBT 与 YAML 别名、深度和数量限制。
- 伪造玩家动作、重复交易、重放请求和恶意资源 manifest。
- 并发连接、反复重载、玩家快速进出和区域边界移动。

### 性能测试

每次性能测试记录：CPU 型号、内存、操作系统、Rust profile、地图 hash、配置 hash、玩家数、实体数、技能频率、测试时长和 p50/p95/p99。没有这些元数据的数字不能用于容量结论。

## 8. 错误、日志与可观测性约定

错误必须带机器可读 code 和人类可读 message，必要时包含：文件、NBT 路径、YAML 路径、区块坐标、玩家 ID、请求 ID 和版本。

建议错误类别：

- `PROTOCOL_*`
- `WORLD_*`
- `CONFIG_*`
- `COMPAT_*`
- `RPG_*`
- `PERSISTENCE_*`
- `SECURITY_*`

日志中不得输出令牌、密码、完整玩家敏感数据或未脱敏的登录信息。调试战斗事件可以使用 hash/ID 关联，生产环境不记录不必要的原始 payload。

## 9. 代码质量门禁

每个实现任务至少满足：

- `cargo fmt --check` 通过。
- `cargo check --workspace` 通过。
- 受影响 crate 的单元和集成测试通过。
- 新增解析器、协议或安全边界具备失败路径测试。
- 公共类型和协议变更更新文档或 ADR。
- 不引入未解释的 `unsafe`；如必须使用，单独 ADR、封装和测试。
- 不在生产路径使用 `unwrap`/`expect` 处理外部输入。
- 基准或压测任务给出可复现命令和结果。

具体命令以项目初始化后的 `CONTRIBUTING.md` 为准；在命令尚未建立前，AI 代理不得伪造“测试已通过”的结果。

## 10. 第一批可直接执行的任务

建议按以下顺序创建 issue：

1. `MC-DOC-001`：冻结版本矩阵、许可证和样例地图来源。
2. `MC-SPIKE-001`：验证 Rust NBT/Anvil 读取并输出地图摘要。
3. `MC-SPIKE-002`：验证客户端 Mod 与服务端 custom payload 往返。
4. `MC-BOOT-001`：创建 Cargo workspace、CI、错误和日志基础设施。
5. `MC-WORLD-001`：实现离线地图检查器。
6. `MC-PROTO-001`：实现协议 fixture、VarInt 和状态机骨架。
7. `MC-SESSION-001`：实现最小 join/quit/keep-alive 会话。
8. `MC-SIM-001`：实现固定 20 TPS tick 和事件提交边界。
9. `MC-RPG-001`：实现属性、伤害和一个技能的原生 IR。
10. `MC-COMPAT-001`：实现 MythicMobs P0 导入器和诊断报告。
11. `MC-VAULT-001`：实现经济服务、幂等事务和审计日志。
12. `MC-CLIENT-001`：实现 UI hello、HUD 和一个音效事件。

## 11. 发布前检查清单

- [ ] 版本矩阵与兼容表已更新。
- [ ] 样例地图可在干净环境导入。
- [ ] 客户端 Mod 与服务端协议版本匹配。
- [ ] 所有配置导入报告已归档。
- [ ] 未支持的 Paper/MythicMobs 机制已明确列出。
- [ ] 经济、物品和玩家存档有恢复测试。
- [ ] 负载、模糊和重放测试通过。
- [ ] 慢 tick、断线、地图损坏和配置错误都有可读诊断。
- [ ] 未分发第三方 jar、Mojang 资产或未确认授权的素材。
- [ ] 运行手册包含启动、导入、备份、恢复和故障排查命令。

## 12. 给 AI 编码代理的启动提示

```text
你正在开发 Mythicraft，一个面向 RPG 的 Rust Minecraft 独立服务端。
先读取 README.md、docs/01-feasibility-analysis.md 和 docs/02-ai-development-plan.md，
再读取当前任务涉及的 ADR、crate 和 fixture。第一版固定 Minecraft 版本，不做地形生成，
不运行 Java Paper 插件；只实现配置/语义兼容子集。所有外部输入必须有长度、深度、类型和权限校验，
所有未知配置和 NBT 数据必须进入结构化诊断。先写最小失败测试，再实现代码，最后运行具体测试和 workspace 检查。
交付时报告修改文件、验证命令、实际结果和剩余限制，不要声称未实际运行的测试通过。
```
